Transporter

Scheduled, encrypted delivery of customer order, inventory, and session data to third-party SFTP servers or API's. A new report is set up as configuration, and every run is watched and encrypted end-to-end. Used for CRM, ERP, warehousing, and financial reporting.

01

The problem

Brands on the platform needed regular extracts of their own business data, pushed into their own systems. Every client had somewhat bespoke needs, and data was sensitive. Security and privacy was sacrosanct.

  1. a Complete data. Every report captures the order, inventory, and/or customer data the client signed up for.
  2. b Their server, not ours. Delivered to the client's secure SFTP server or API.
  3. c Their keys. Encrypted with OpenPGP or GPG, with keys usually held by the client.
  4. d Their format. XML, JSON, CSV, TSV, or XLSX, with the client's column names and file-naming rules.

03

How it works

Two Lambdas, split by job. One manages configuration and is only reachable by the team. The other runs on schedule: it reads a job's config, pulls the data, then formats, encrypts, and sends it.

04

Decisions that mattered

Serverless, scheduled jobs

Reports run on a schedule and in bursts, so each run is a Lambda invocation rather than a server sitting idle between deliveries.

A new client is config, not code

File format, columns, naming, schedule, and destination live in one DynamoDB record per job, type-checked when they're saved.

Secrets never stored in the clear

Each job has its own credentials, and those plus its encryption keys are AES-256 encrypted before they're written. Files are PGP-encrypted to the client's key before they leave.

Least access to the controls

The scheduler API sits behind auth middleware, and only developers and project managers can configure, test, or save a job.

What I built
